# Proposal: Распознавание квитанции по фото (локальный OCR, без LLM)

## Зачем
Ввод сумм вручную — основная рутина. У пользователя есть скриншоты платёжных документов
(пример: «Фурманова 193», август 2026, 5 документов, «К оплате 8 292,04 ₽»). Нужно:
загрузил изображение в форме месяца → суммы разложились по статьям расходов.
Требование пользователя: **распознавание локальное, без LLM** — данные не уходят ни в
какие внешние сервисы.

## Что делаем

### 1. Локальный OCR в браузере
- Tesseract.js v5 (WASM) + русский языковой пакет; ассеты лежат в репозитории
  (`vendor/tesseract/`) и отдаются с GitHub Pages → не зависим от CDN и блокировок сети.
- Предобработка изображения на canvas перед распознаванием (масштаб ~1600px, grayscale,
  контраст) — повышает точность на мелком шрифте квитанций.
- Первая загрузка ~5 МБ (движок) + ~2 МБ (русский traineddata), дальше — HTTP-кэш браузера.

### 2. Сопоставление строк со статьями — по реквизиту «Соответствие ГИС ЖКХ»
В документах строки содержат название получателя: «МУП города Хабаровска», «ООО "Магнит"»,
«ООО "РЕГСТРОЙКОМ"», «Филиал ПАО "ДЭК"» (Хабаровскэнергосбыт).
- У каждой статьи расходов появляется реквизит **«Соответствие ГИС ЖКХ»** — подстроки-получатели
  через «;». Пользователь заполняет соответствия один раз.
- Парсер ищет статью сначала по этому реквизиту (нормализация регистра, кавычек, пробелов и
  типовых OCR-ошибок: «ООО»→«000», «₽»→«Р»/«е», латиница в кириллице), затем — по словарю
  синонимов услуги (Коммунальн/Электро/Вода/ТКО/Домофон/Капремонт/Отоплен/Газ/ТВ).
- **Несколько документов одного получателя суммируются в одну статью** (проверено на скриншоте:
  «ООО "Магнит"» документы N21 = 4865,20 и N22 = 961,07 — обе квартплата → 5826,27 в статью
  «Квартплата»). Если у получателя несколько РАЗНЫХ статей — строка уходит в превью на ручной выбор.
- Строка, не нашедшая статью, не теряется: в превью помечается «не распознано» с выбором статьи.

### 3. Превью и применение
- Показывается таблица «распознано → статья → сумма» с возможностью правки и выбора статьи
  для спорных строк; контрольная сверка с итогом квитанции («К оплате N ₽»).
- Кнопка «Применить» заполняет поля формы месяца; запись в БД — только по обычной кнопке
  «Сохранить» (никаких изменений данных без подтверждения).
- Показания счётчиков из квитанции заполняются в те же поля (вода х/г с учётом кухня/ванная,
  электро день/ночь), если распознаны.

## Схема БД
- `payment_items` + колонка `gis_match text` (NULL-able; список подстрок через «;»).
  Миграция через Supabase Management API: `ALTER TABLE payment_items ADD COLUMN IF NOT EXISTS gis_match text`.
- Другие таблицы не меняются. Распознавание в БД не пишет.

## Архитектура
- `vendor/tesseract/`: `tesseract.min.js`, `worker.min.js`, `tesseract-core.wasm.js` (~4,7 МБ),
  `rus.traineddata` (~2 МБ). Ленивая загрузка при первом использовании, дальше HTTP-кэш.
- `js/ocr.js` — загрузка воркера, предобработка изображения, вызов распознавания.
- `js/receipt-parse.js` — парсер: нормализация, сопоставление со статьями (gis_match → синонимы),
  извлечение сумм и показаний, сверка итога.
- `js/app.js` — кнопка «С квитанции», превью, применение в форму.
- Supabase в распознавании не участвует.

## Границы
- Сейчас — только изображения (фото/скриншоты). PDF-квитанции (ДЭК присылает по e-mail) — отдельной задачей.
- Детализации по услугам внутри одного платёжного документа в текущих скриншотах нет — раскладка
  идёт по получателю и его соответствиям.
