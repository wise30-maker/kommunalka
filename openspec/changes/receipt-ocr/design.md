# Design: Распознавание квитанции по фото

## Ключевые решения

### Почему локальный OCR в браузере, а не LLM/сервер
Требование пользователя — распознавание локальное, без LLM. Дополнительно: сайт статический
(GitHub Pages), серверного кода нет; отправка фото квитанции на внешний API означала бы
передачу персональных данных (лицевой счёт, адрес) третьей стороне.

### Почему Tesseract.js и ассеты в репозитории
- Tesseract.js v5 (WASM) работает в Safari на iPhone и в десктопных браузерах.
- Сеть пользователя ограничена allowlist'ом; внешние CDN могут оказаться недоступны.
  Поэтому `tesseract.min.js`, `worker.min.js`, `tesseract-core.wasm.js`, `rus.traineddata`
  лежат в `vendor/tesseract/` и раздаются с GitHub Pages.
- Загрузка ленивая: движок тянется только при первом нажатии «С квитанции», дальше из кэша.

### Предобработка изображения
Скриншот 1284×2778 (iPhone) уменьшается до ~1600px по большей стороне, переводится в grayscale,
поднимается контраст. Это ускоряет распознавание и сглаживает артефакты JPEG.

### Модель сопоставления «получатель → статья»
```
текст OCR → строки
  ├─ нормализация (регистр, кавычки “ ” « » ", пробелы, OCR-ошибки 0↔О, 6↔б, ₽→Р/е)
  ├─ приоритет 1: gis_match статьи (подстрока получателя, несколько через «;»)
  ├─ приоритет 2: словарь синонимов услуги
  └─ иначе: строка «не распознано» → ручной выбор статьи в превью
суммы строк, попавших в одну статью, складываются
```
Пример из скриншота «Фурманова 193» (август 2026, 5 документов):
795,63 (МУП г. Хабаровска) + 4865,20 (Магнит N21) + 961,07 (Магнит N22) +
567,56 (РЕГСТРОЙКОМ) + 1102,58 (ДЭК) = **8 292,04 ₽** = «К оплате» в квитанции.
Проверка суммы служит контролем качества распознавания: если расхождение больше копеек —
в превью выводится предупреждение.

### Как извлекается сумма
Сумма — последнее число в строке/блоке документа: шаблон `\d{1,3}(?:[ \u00a0]\d{3})*[.,]\d{2}`
либо `\d+[.,]\d{2}`, нормализация запятой в точку. Числа, похожие на номера документов (N21, N22),
отсекаются требованием двух знаков после разделителя и наличия валютного признака в блоке.

### Разбор показаний счётчиков
Ищем блок «Показания»; строки сопоставляем с kind/zone: вода холодная/горячая (кухня/ванная —
если у объекта `split_water`), электро день/ночь. Если блок не распознан — поля остаются пустыми,
это не блокирует применение сумм.

### Превью перед записью
Двухшаговость критична: распознавание не пишет в БД. Пользователь видит сопоставление, правит,
и только потом «Применить» → поля формы → «Сохранить» пишет в Supabase как обычно.

## Инструмент разработки: OCR Windows для отладки парсера
На машине разработки проверено: встроенный Windows.Media.Ocr (PowerShell + WinRT) распознаёт
те же скриншоты локально, движок `ru` доступен (скрипт `tools/winocr.ps1`, вывод в UTF-8).
Используется как быстрый оффлайн-стенд для отладки парсера без телефона.

## Риски
| Риск | Смягчение |
|---|---|
| Точность tesseract на мелком шрифте | предобработка + превью с правкой + сверка с итогом квитанции |
| ~7 МБ ассетов в репозитории и в каждом деплое | инкрементальный деплой (пропуск неизменившихся blob'ов по git-hash) |
| Один получатель — несколько разных статей | ручной выбор статьи в превью |
| Новые получатели в квитанциях | поле «Соответствие ГИС ЖКХ» заполняется пользователем без правки кода |
| PDF-квитанции ДЭК | отдельная задача (текстовый слой PDF / конвертация) |
