# Design

## Context

См. proposal.md (Why). Ключевые ограничения: бесплатный хостинг без сервера
(статика), доступ с телефона и ПК, один пользователь-владелец, сеть разработчика
ограничена (PyPI/npm недоступны — сборка фронтенда не должна их требовать),
GitHub доступен только через API (api.github.com, codeload.github.com) с токеном.

## Goals / Non-Goals

**Goals:**
- Одностраничное приложение на vanilla JS (без сборки, без npm-зависимостей),
  работающее на GitHub Pages.
- Supabase (Postgres + Auth, бесплатный tier) как бэкенд: данные, авторизация,
  RLS-правила.
- Удобный ввод с телефона (крупные поля, числовая клавиатура).
- Миграция истории из `Таблица (13).xlsx`.

**Non-Goals:**
- Расчёт расхода по счётчикам и тарифам (показания — справочно).
- Мультпользовательский доступ, роли, совместное редактирование.
- Офлайн-режим / PWA.
- Импорт Excel из интерфейса сайта (миграция — однократная процедура разработчика).

## Decisions

### D1. Хостинг — GitHub Pages, деплой через GitHub API

Статика на GitHub Pages + деплой коммитами через REST API с токеном
(`contents` + `pages` endpoints). `gh` CLI на машине не установлен, SSH-ключ не
привязан к аккаунту — используем предоставленный пользователем токен
(переменная окружения `GITHUB_TOKEN`, в репозиторий не коммитится).

Альтернативы: Netlify/Vercel (нужен их аккаунт, лишняя зависимость);
Neocities (нет HTTPS-авторизации под наш сценарий с API, слабее интеграция).
GitHub Pages проще: один аккаунт, один токен, всё в одном месте.

### D2. Бэкенд — Supabase

Postgres + встроенный Auth (email/password) + REST API (PostgREST) +
Row Level Security. Фронтенд ходит в Supabase напрямую с JWT; RLS-политики
ограничивают доступ владельцем. Таблицы:

```
objects          id, name, sort_order, water_zones (jsonb: зоны воды)
payment_items    id, object_id → objects, key (квартплата|электро|вода|тко|
                 домофон|капремонт|отопление|газ|тв), title, sort_order
periods          id, object_id → objects, year, label (напр. "Август + Сентябрь"),
                 sort_key (для хронологического порядка)
payments         id, period_id → periods, item_id → payment_items, amount numeric
meter_readings   id, period_id → periods, kind (water_cold|water_hot|elec_day|
                 elec_night), zone (nullable: кухня/ванна), value numeric
```

Итог за период — сумма `payments.amount` по периоду, считается на лету запросом,
не хранится (устраняет класс багов «итог рассчитан руками и разошёлся»).

Альтернативы: Firebase (NoSQL, сложнее отчёты); Google Sheets как БД (данные
светятся по ссылке, гонки записи); собственный бэкенд на бесплатном хостинге
(не влезает в бесплатные лимиты, требует обслуживания).

### D3. Фронтенд — vanilla JS, один HTML-файл с модулями, без сборки

Один `index.html` + несколько JS-модулей (ES modules) + CSS. Работа с Supabase
через официальный JS-клиент (один `.js`-файл, подключается локально — CDN
нежелателен из-за возможных блокировок в сети пользователя). Отчёты — рисование
на `<canvas>` вручную, без chart-библиотек.

Альтернативы: React+сборка (npm заблокирован в сети разработчика, избыточно);
Vue через CDN (зависимость от внешнего CDN в рантайме).

### D4. Год как обязательное измерение периода

В Excel годов не было — месяцы шли подряд через границы года. В модели `year`
обязателен; склеенные периоды хранят `year` года начала и текстовую `label`.
Хронологический порядок — поле `sort_key` (YYYY.MM или дробный индекс для
склеенных периодов), потому что подписи вроде «Март\Апрель» лексикографически
не сортируются.

### D5. Миграция — однократный скрипт

Python-скрипт (stdlib: zipfile + XML-парсинг xlsx, openpyxl недоступен — PyPI
заблокирован) читает все 5 листов Excel, маппит статьи/показания на модель и
заливает в Supabase через REST API с upsert по естественному ключу
(object + year + label). Склеенные периоды («Ноябрь\декабрь») переносятся как
есть, с `label` из Excel.

## Risks / Trade-offs

- [Supabase приостановит проект при ~7 днях неактивности на free tier] →
  фронтенд при запуске делает лёгкий запрос к API; при неактивности нужен первый
  запуск после паузы (прогрев ~10–20 с), либо позже внешний пинг по cron.
- [Токен GitHub в переменной окружения теряется при сбросе сессии] → держать
  запись в локальном файле вне репозитория (например, `%USERPROFILE%\.kommunalka-github-token`)
  с пометкой «не коммитить».
- [Склеенные периоды ломают помесячную динамику в отчётах] → в отчётах
  склеенный период показывается одной точкой с его `label` (как в Excel),
  это осознанное упрощение.
- [Миграция из Excel: часть итогов в Excel битые (формулы без колонки)] →
  сайт считает итог сам из внесённых статей; расхождения с Excel-итогом —
  источник истины Excel-статьи, а не Excel-итог.

## Migration Plan

1. Создать репозиторий `kommunalka` в GitHub (через API, токен), включить Pages
   (branch `main`, корень `/`).
2. Реализовать фронтенд, деплоить коммитами через API.
3. Завести проект Supabase, создать таблицы и RLS-политики, создать
   пользователя-владельца.
4. Внести URL/anon-key Supabase в конфиг фронтенда, задеплоить.
5. Прогнать миграционный скрипт, сверить итоги по выборочным месяцам.
6. Открыть сайт с телефона, проверить вход и ввод.

Откат: старый Excel-файл и архив БД (pg_dump перед миграцией) — полный откат
на шаг 0.
